# Direct streaming: findings

**Started:** 2026-11-15
**Plan:** `.workflows/plan/DIRECT_STREAMING_PLAN.md` (phase 2 writes everything above **Playback**; phase 6 writes **Playback**)
**Brief:** `docs/plans/2026-11-15-direct-streaming-design.md`

The brief left these untested: the other 18 providers, why three providers returned nothing,
series episodes, how long a manifest's token lives, and playback (DASH, VidNest, subtitles in our
player). This file holds what was measured on the owner's laptop through the streaming Chrome.

The tables between `<!-- campaign:... -->` markers are generated by
`claude/streaming/direct/campaign.mjs`. Rerun the command; never edit them by hand.

## How it was measured

- `node claude/streaming/direct/campaign.mjs run` probes all 24 seed providers and writes the
  tables below; `report <results.json>... --lifetime <log.jsonl>` rewrites them from saved results
  (a later file's row replaces an earlier one's, so `run --only <name>` after a fix updates one
  row); `apply-seed <results.json>...` fills `tv`, `en_subtitle`, `browser_only` and `notes` in
  `claude/streaming/direct/providers.seed.json`; `check` confirms this file and the seed agree.
- Each provider is probed through the resolver the daemon uses (`resolveTitle` with that one
  provider), so a provider counts as resolved exactly when `/direct-stream` would play it.
- Titles: Fight Club (TMDB movie 550), Sinners (TMDB movie 1233413, 2025) as the recent film,
  Breaking Bad S02E03 (TMDB tv 1396) as the series episode. Breaking Bad S01E99 is the control: the
  first season has seven episodes, so a template that also resolves S01E99 ignores the episode.
- A provider that does not resolve Fight Club, and Videasy, VidKing and CloudPlay always, get a
  second sniff of 90 s with `-Inspect`: the sniffer reads every frame's video elements, iframes and
  visible text before it closes the tab. Nothing is clicked by the inspection.
- Each resolved manifest is fetched once from WSL with the headers the real Chrome sent, for the
  subtitle tracks and heights it names and to see whether the pass-through approach works for that
  provider (`node_fetch_status` in the raw results).
- The streaming Chrome (`notesd-stream-chrome`, port 9333) stays minimized and muted. No window was
  brought forward and nothing played with sound.
- Raw results carry manifest addresses with tokens, so they stay in
  `~/.local/state/notesd-direct-campaign/`, outside git. Each table names the files it came from.

## Failure causes

| Cause | Meaning | Evidence that names it |
| --- | --- | --- |
| `bot_check` | the embed answered with a bot check; skipped, never worked around | the resolver's outcome, or the sniffer's `bot_check` flag (a "Just a moment" title or a challenge frame) |
| `error` | the sniff itself failed | every run errored; the raw result's `detail` says how |
| `unreachable` | the embed host did not answer | at most one request in every run, or the tab ended on Chrome's own error page (DNS failure, time-out) or on Cloudflare's 52x "origin is down" page |
| `not_found` | the provider does not have this title | the recent film resolved but Fight Club did not, or a frame's text says not found, no sources, unavailable or 404 (the text of a page on an unrelated host, an advert that took the tab over, is not counted) |
| `blob_media` | the video plays through MSE from addresses the sniffer does not recognise as a stream | a `<video>` with a `blob:` source and data, and no manifest request; such a provider cannot feed our player and is `browser_only` |
| `frame_not_attached` | the player is in a frame the sniffer never attached to | the page has iframes, the sniffer saw none |
| `click_missed` | a player is there and waits; the sniffer's clicks at the page centre did not start it | a video element or player frame, nothing started, clicks sent |
| `no_player` | the page shows no player at all | no video element and no iframe in any readable frame |

Notes on a provider that resolved: `slow_start` (only the 90 s sniff resolved), `needed_click`
(the stream came after the sniffer clicked), `not_reproduced` (one of the spike's three silent
providers resolves now).

## Why three returned nothing

In the spike, Videasy, VidKing and CloudPlay (`vidsrc.cc`) gave no stream in 35 s, each with under
ten requests. The procedure, for each of them:

1. **Request count and hosts.** The standard sniff's `requests` and top hosts. At most one request
   means the host did not answer (`unreachable`); a handful on the embed host alone means the page
   stopped early (a check, an error page, or a script that waits).
2. **Bot check.** The sniffer's `bot_check` flag and the page title (`bot_check`).
3. **Frames.** Which frames the sniffer attached to, against the iframes the page has
   (`frame_not_attached`).
4. **Longer wait.** The 90 s sniff: a stream that shows up only there is `slow_start`.
5. **Click needed.** The sniffer clicks the page centre after 8 s, up to four times; a stream after
   a click is `needed_click`, a player still waiting after them is `click_missed`.
6. **Blob or MSE-only media.** The inspection's video elements: a `blob:` source with data and no
   manifest request is `blob_media`.
7. **Another title.** The recent film resolving where Fight Club did not is `not_found`.

### Videasy

**Cause:** `unreachable`

**Evidence:** 5 requests in the standard sniff and 5 in the 90 s one, no frame, no media hit.
The raw hosts are `player.videasy.net` (1 request) and `player.videasy.to` (1 request): the embed
forwards to `player.videasy.to`, and that name does not resolve on this network. The inspected
tab is Chrome's own error page (`chrome-error://chromewebdata/`, "This site can't be reached ...
`DNS_PROBE_FINISHED_NXDOMAIN`"). Sinners fails the same way, so it is the host, not the title.
No sniffer change: there is nothing to sniff.

### VidKing

**Cause:** `unreachable`

**Evidence:** 4 requests in each sniff, all for `www.vidking.net` (1 counted host), no frame, no
media hit. The inspected tab is Chrome's error page: "This site can't be reached", a DNS failure
for `www.vidking.net`. Sinners fails the same way. No sniffer change.

### CloudPlay

**Cause:** `unreachable`

**Evidence:** 8 requests in each sniff, every one to `vidsrc.cc`, no frame, no media hit. The
name resolves and Cloudflare answers, but its origin does not: the inspected page is Cloudflare's
"522: Connection timed out" (14:01 UTC, Jakarta edge). Sinners fails the same way. No sniffer
change.

### What the three have in common

None of them is a sniffer miss, a slow start, a missed click or a bot check: in each case the
provider's own host did not serve a page, which is why the spike saw under ten requests. Seven
more seed providers fail the same way today (Peachify 523, UltraBox, CloudBox and UpCloud 521,
StreamVault and MovieVault time-outs, StreamBoxHD DNS). Whether the two DNS failures are the
providers' or this network's resolver was not measured; from this laptop they are unusable either
way, and the daemon's per-host health will keep them last.

## Sniffer changes

- `-Inspect` (phase 2): `sniff.ps1 -Inspect` / `sniffEmbed(url, { inspect: true })` reads, in the
  page and each frame the sniffer attached to, the video elements (source, ready state, position),
  the iframe count, the title and the first 300 characters of visible text, just before the tab
  closes. It clicks nothing and plays nothing. Without it the sniffer behaves as before. Added
  because `blob_media` and `frame_not_attached` cannot be told apart from network requests alone.
- Short mp4 clips are not streams (phase 2). Finding: VidMov's 90 s sniff "resolved" in 28.8 s
  with an `mp4` from `cdn.cloudpiko.com`, a gambling advert clip (206, `video/mp4`), and any mp4
  request also ended the watch 12 s later. `sniff.ps1` now drops an mp4 answer whose
  `Content-Range` total (or `Content-Length`) is under 20 MB and does not let it end the watch.
  Confirmed by `run --only NonTongo,VidSrc,HyperLink,VidMov --out .../rerun-1`: VidMov is
  `no_stream`, cause `click_missed`.
- The diagnosis, not the sniffer, was corrected twice after reading the raw results: a tab that
  ends on Chrome's error page or a Cloudflare 52x page is `unreachable` (ten providers were first
  named `no_player`), and the text of an advert page that took the tab over is not read as the
  provider's answer (Movies111 ended on `ron.mamma.com`'s 404 page and was first named
  `not_found`). `report` and `apply-seed` work the verdicts out again from the raw sniffs.
- Seen and left alone:
  - `click_missed` for VidMov, VidFyi and VidSrc: all three wrap `vidsrc.sh`, whose player sits
    in a nested `stellarconductornexus.com` frame and waits for a press; the sniffer's clicks at
    the page centre do not reach it. Pressing inside a nested frame was not built: on these
    pages a press is as likely to open an advert as to start the film.
  - `bot_check` for NonTongo and MediaHub comes from a request to Cloudflare's
    `/cdn-cgi/challenge-platform/`, not from a visible check: NonTongo's page showed its player
    and resolved Sinners once in 28.8 s in the first run (not in the re-run), and MediaHub now
    serves a "Coming Soon" page. The flag ends the sniff after 5 s. It was not loosened: a bot
    check is an outcome and is never worked around.
  - A manifest request that never gets an answer (VidNest's `master.txt` and HyperLink's
    `cdn2.slowcloud.live` address, both for Fight Club) is a hit without a status and is rightly
    not a stream; both providers resolve Sinners, so the table names them `not_found`.
- Re-run: an lk21 play from another session used the streaming Chrome between 13:39 and 13:43 UTC
  and closed its other tabs, so NonTongo, VidSrc and HyperLink (probed around then) were probed
  again in `rerun-1`, with VidMov; their rows come from the re-run.

Measured with `claude/streaming/direct/playcheck.mjs` against a throwaway daemon started from the
worktree (`verify.sh up --web --direct-stream`: its own port, database and data dir; the real resolver
behind `NOTESD_DIRECT_STREAM_CLI`, wrapped so the daemon's play never opens Chrome itself). Each
run opens one session's player page in the streaming Chrome, muted, in a normal window, never
full screen, and samples the `<video>` every 1.5 s. The table between the markers is generated by
`node claude/streaming/direct/playcheck.mjs findings`; do not edit it by hand. Re-running a check
replaces its row and counts the run.

### How a result is decided

- **plays**: the video advanced at least 10 s at a real resolution and was playing at the end. A
  subtitle check also needs an English text track in mode `showing` with cues. An expiry check
  needs the first source refused by the gate, a second resolve served, and playback going on no
  more than 10 s before where it stopped.
- **browser_only**: it did not play, and a cause no pass-through can remove is named: `drm` (a
  DASH `ContentProtection`, an HLS key format other than identity, or a key-system error),
  `encrypted_segments` (SAMPLE-AES, or an AES-128 key the player cannot load) or
  `obfuscated_segments` (the first segment is not TS, fMP4, AAC or ID3, for example a PNG header).
  The provider is marked `"browser_only": true` in the seed with the cause in `notes`.
- **needs_fix**: it did not play, or the subtitle or the refresh failed, with no such cause. The
  fault is treated as ours. A fix in `web/src/stream` lands with a failing test first and a row
  in Fixes; a fault in the daemon's pass-through stays open with a task.
- **no_source**: the provider did not resolve during the run; after 3 runs at least 5 minutes
  apart it is recorded as "did not resolve during the campaign", not as browser_only.
- **inconclusive**: the run could not look (Chrome, tab, daemon, a stop for sound or full screen)
  or the check did not apply (a DASH check served HLS, no English track offered). It decides
  nothing and is run again.

"First frame" counts from the moment the play was asked for, so it includes the resolve (5 to 11 s).

- DASH (VidLink, Fight Club 550): plays. 1154x482 (the manifest's only level is 480p, h265), first
  frame at 9.5 s, 2 dropped of 424 frames, 54.5 s buffered, no `ContentProtection`. Three runs: the

- VidNest, HLS (Sinners 1233413; phase 2 measured that VidNest has no Fight Club): plays, twice.
  1920x696, one level, 0 dropped of 401 frames, 33.5 s buffered; first frame at 10.9 s on the first

  VidRock's segments are disguised the same way and also played. So a disguised first segment
  alone is not a `browser_only` cause; `decide` only reads it when the video did not play.
- English subtitle from a separate file (NexaStream, Fight Club 550): plays. Track `en`, mode
